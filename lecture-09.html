Вертикальне vs горизонтальне масштабування

Scale up (вертикальне)

  • Більше ядер / RAM / швидші диски одній машині.
  • Фізичний ліміт апаратури.
  • Нелінійне зростання вартості топового заліза.
  • Єдина точка відмови — падіння машини = зупинка сервісу.

Scale out (горизонтальне)

  • Нові однакові копії застосунку за балансувальником.
  • Без архітектурного ліміту зростання.
  • Копії підіймаються/знищуються автоматично за метриками.
  • Відмова копії не зупиняє систему.

У Cloud-native середовищах горизонтальна модель — основна: саме вона реалізується контейнерами та оркестрацією.

Scale Cube — три осі зростання

  • Вісь X (Horizontal Duplication) — клонування: N ідентичних копій застосунку за балансувальником, кожна обробляє будь-який запит.
  • Вісь Y (Functional Decomposition) — декомпозиція: моноліт → сервіси за бізнес-можливостями (теми 4-5, Controller — Service — Repository).
  • Вісь Z (Data Partitioning) — шардування: кожна копія обслуговує свій зріз даних (регіон, діапазон ID, хеш ключа).

Порядок застосування: X → Y → Z. Вісь X — перший крок: нуль змін у коді, той самий артефакт запускається у копіях. Ця лекція — про вісь X.

Stateless — передумова осі X

Stateful (сесії в пам'яті)

  • Стан користувача — у процесі.
  • Балансувальник змушений тримати sticky sessions.
  • Нерівномірне навантаження на копії.
  • Видалення копії = втрата сесій користувачів.

Stateless (JWT, тема 8)

  • Ідентифікаційний стан — у токені.
  • Спільні дані — у PostgreSQL / MongoDB / Redis.
  • Будь-яка копія обробляє будь-який запит.
  • Копії взаємозамінні — свобода масштабування.

Виняток — WebSocket: довгоживучі з'єднання прив'язані до інстансу → ip_hash або Redis-адаптер (питання 5).

Node.js — модуль cluster

Один процес Node.js = один event loop = одне ядро. Cluster запускає по воркеру на кожне ядро: primary приймає з'єднання, воркери обробляють незалежно.

const cluster = require('cluster');
const os = require('os');

if (cluster.isPrimary) {
  const workers = os.availableParallelism();   // логічні ядра
  for (let i = 0; i < workers; i++) cluster.fork();

  // Самовідновлення: впалий воркер перезапускається
  cluster.on('exit', (worker, code) => {
    console.log(`worker ${worker.process.pid} died (${code})`);
    cluster.fork();
  });
} else {
  const app = express();
  app.get('/health', (_q, res) => res.json({ pid: process.pid, up: true }));
  app.listen(3000);   // кожен воркер слухає той самий порт
}

Node.js — PM2 у cluster-режимі

// ecosystem.config.js
module.exports = {
  apps: [{
    name: 'node-api',
    script: './src/server.js',
    instances: 'max',              // воркер на кожне ядро
    exec_mode: 'cluster',
    max_memory_restart: '512M',   // захист від Memory Leaks
    env: { NODE_ENV: 'production' },
  }],
};

# Запуск і горизонтальне масштабування до 4 воркерів:
pm2 start ecosystem.config.js
pm2 scale node-api 4

PM2 автоматизує той самий патерн: моніторинг стану, авто-перезапуск, ліміти пам'яті.

Go — один процес на всі ядра

package main

import (
	"log"
	"net/http"
	"runtime"
)

func main() {
	// Кожен запит — окрема горутина, планувальник M:P:N
	// розподіляє їх по всіх ядрах (GOMAXPROCS = NumCPU).
	log.Printf("GOMAXPROCS = %d", runtime.GOMAXPROCS(0))

	http.HandleFunc("/health", func(w http.ResponseWriter, r *http.Request) {
		w.Write([]byte(`{"up":true}`))
	})
	log.Fatal(http.ListenAndServe(":8080", nil))
}

Go: одна репліка ≈ всі ядра хоста. Node.js: репліка ≈ одне ядро → численніші дрібніші копії. У контейнерах узгоджуйте GOMAXPROCS із квотою CPU (automaxprocs).

Forward Proxy vs Reverse Proxy

Forward Proxy — від імені клієнтів

  • Приховує користувачів від серверів.
  • Корпоративні шлюзи, фільтрація.
  • Клієнт знає про проксі та налаштовує його.

Reverse Proxy — від імені серверів

  • Приховує внутрішні сервіси.
  • Клієнт бачить одну публічну адресу.
  • Клієнт навіть не знає, що за нею група копій.

Nginx — зворотний проксі корпоративного рівня: подійна архітектура (epoll/kqueue), десятки тисяч паралельних з'єднань при мінімальній пам'яті.

Архітектурна роль Reverse Proxy

  • Єдина точка входу (порти 80/443) — сервіси не мають публічних маршрутів (expose, не ports).
  • Ізоляція топології — клієнт не знає кількість та адреси копій.
  • Єдине TLS-термінування та заголовки безпеки (тема 8).
  • Кешування статики та проксованих відповідей.
  • Буферизація повільних клієнтів — захист event loop / горутин.
  • Таймаути, rate limiting — централізований периметр.
  • HTTP/2 до браузерів та gzip — рутини поза застосунками.

Базовий nginx.conf — proxy_pass

worker_processes auto;          # воркер на кожне ядро
events { worker_connections 1024; }

http {
    upstream node_backend {       # група Node.js-сервісів
        server node-app-1:3000;
        server node-app-2:3000;
    }
    upstream go_backend { server go-app:8080; }

    server {
        listen 80;
        server_name api.example.com;

        location /api/users {            # → флот Node.js
            proxy_pass http://node_backend;
            proxy_set_header Host $host;
            proxy_set_header X-Real-IP $remote_addr;
            proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
            proxy_set_header X-Forwarded-Proto $scheme;
        }
        location /api/reports {          # → Go-сервіс
            proxy_pass http://go_backend;
            proxy_set_header Host $host;
        }
    }
}

proxy_set_header обов'язковий: без нього застосунок побачить адресу Nginx та HTTP замість справжніх даних клієнта.

WebSocket-проксіювання та hot reload

# WebSocket потребує явного Upgrade (тема 6)
location /ws {
    proxy_pass http://node_backend;
    proxy_http_version 1.1;
    proxy_set_header Upgrade $http_upgrade;
    proxy_set_header Connection "upgrade";
    proxy_read_timeout 600s;   # довгоживучі з'єднання не рвуться
}

# Зміна конфігурації без зупинки трафіку:
nginx -t && nginx -s reload

Без Upgrade-заголовків Nginx трактує з'єднання як звичайний HTTP-запит і розриває його після таймауту.

Load Balancer — L4 vs L7

  • L4 (транспортний) — балансування TCP-потоків, без розбору протоколу: швидко, але сліпо до URI.
  • L7 (застосунку) — повний HTTP-контекст: URI, заголовки, cookies. Nginx цієї лекції — L7: бекенд обирається окремо для кожного запиту.

Наслідки L7: маршрутизація різних URI до різних стеків, повтор помилкових запитів на іншій копії, «розумні» алгоритми на основі вартості обробки.

Round Robin та Weighted

Round Robin (дефолт)

  • Запити роздаються по колу.
  • Однакові інстанси, однакова вартість запитів.
  • Найпростіший і найпередбачуваніший.
upstream rr {
    server node-app-1:3000;
    server node-app-2:3000;
    server node-app-3:3000;
}

Weighted Round Robin

  • Ваги для різних потужностей.
  • 3 з 4 запитів — на потужний хост.
upstream wrr {
    server node-app-1:3000 weight=3;
    server node-app-2:3000 weight=1;
}

Least Connections та IP Hash

Least Connections

  • Запит → інстансу з найменшою кількістю активних запитів.
  • Самовирівнювання при нерівномірній тривалості.
  • Вибір за замовчуванням для Node.js: важкий запит займає воркер надовго.
upstream lc {
    least_conn;
    server node-app-1:3000;
    server go-app:8080;
}

IP Hash

  • Хеш IP клієнта → той самий інстанс (sticky).
  • Для legacy-сесій та стабільності WebSocket.
  • Обмеження: нерівномірність за NAT, втрата стану при падінні інстансу.
upstream ih {
    ip_hash;
    server node-app-1:3000;
    server node-app-2:3000;
}

Відмовостійкість upstream

  • Пасивні health checks (open-source Nginx): помилки фіксуються на клієнтському трафіку.
  • max_fails=3 fail_timeout=30s — 3 збої за 30 с → інстанс поза ротацією на 30 с.
  • proxy_next_upstream — помилковий запит одразу повторюється на наступній копії.
  • backup — запасні сервери активуються, коли всі основні недоступні.
  • Активні перевірки — healthcheck у docker-compose (питання 3.3).
upstream node_backend {
    least_conn;
    server node-app-1:3000 max_fails=3 fail_timeout=30s;
    server node-app-2:3000 max_fails=3 fail_timeout=30s;
    server go-app:8080 backup;
}
# ...

Особливість: статичний upstream резолвить імена один раз при старті — нові адреси копій потрібують resolver зі змінною.

Для курсового проєкту достатньо детермінованої схеми з переліченими копіями — конфігурація читається як документ архітектури.

Кешування статичних активів

proxy_cache_path /var/cache/nginx/static
                 levels=1:2
                 keys_zone=static_cache:10m
                 max_size=1g inactive=60m;

server {
    location /static/ {              # статику роздає сам Nginx
        root /var/www/app;
        expires 30d;                  # кеш браузера 30 днів
        add_header Cache-Control "public, immutable";
    }
    location /api/catalog {           # кеш відповіді застосунку
        proxy_pass http://node_backend;
        proxy_cache static_cache;
        proxy_cache_valid 200 10m;
        proxy_cache_valid 404 1m;
        add_header X-Cache-Status $upstream_cache_status;  # HIT/MISS
    }
}

Два напрямки: кеш браузера (expires, immutable для версіонованих імен app.1a2b3c.js) та кеш проксі (proxy_cache_valid за статусами).

Буферизація — проблема повільних клієнтів

Без проксі: повільний мобільний клієнт тримає event loop воркера Node.js (або горутину Go) десятки секунд лише через погану мережу.

Nginx-проксі: читає відповідь бекенда на повній швидкості внутрішньої мережі у власні буфери, стрімить клієнту в його темпі — застосунок звільняється негайно.

location /api/ {
    proxy_pass http://node_backend;
    proxy_buffering on;              # on за замовчуванням
    proxy_buffer_size 4k;            # буфер заголовків
    proxy_buffers 16 4k;             # 16 робочих буферів
    proxy_busy_buffers_size 8k;      # прямий відданний потік

    # Обмеження тіла запиту (захист від гігантських upload-ів)
    client_max_body_size 10m;
    client_body_buffer_size 128k;    # до 128 КБ — лишається в RAM
}

Таймаути та rate limiting

Таймаути — страховка

  • proxy_connect_timeout 3s — TCP-handshake.
  • proxy_send_timeout 5s — передача запиту.
  • proxy_read_timeout 30s — відповідь (дефолт 60s).
  • Разом з proxy_next_upstream — автоматичний failover.

Rate limiting (OWASP A04)

  • limit_req_zone ... rate=10r/s — leaky bucket: 10 МБ ≈ 160 000 IP.
  • limit_req zone=api_limit burst=20 nodelay — дозволений пік.
  • limit_conn — ліміт паралельних з'єднань з IP.
  • Для логіна — окрема зона auth_limit rate=1r/s (антибрутфорс, тема 8).

SSL Termination

TLS закінчується на Nginx — всередині docker-мережі трафік рухається відкритим HTTP. Сервіси позбавлені менеджменту сертифікатів та CPU-вартості handshake.

server {
    listen 80;
    return 301 https://$host$request_uri;   # весь HTTP → HTTPS
}

server {
    listen 443 ssl;
    http2 on;
    ssl_certificate     /etc/nginx/certs/fullchain.pem;
    ssl_certificate_key /etc/nginx/certs/privkey.pem;
    ssl_protocols       TLSv1.2 TLSv1.3;    # SSLv3, TLSv1.0/1.1 заборонені
    ssl_session_cache   shared:SSL:10m;     # повторні handshake без CPU
    ssl_session_timeout 10m;
    add_header Strict-Transport-Security "max-age=31536000" always;

    location / {
        proxy_pass http://node_backend;
        proxy_set_header X-Forwarded-Proto $scheme;  # застосунок знає про https
    }
}

Вибір стратегії під стек

Node.js флот

  • Численніші дрібні репліки (1 репліка ≈ 1 ядро).
  • least_conn вирівнює нерівномірні запити.
  • Вихід однієї репліки коштує 1/N потужності.
  • Жодних сесій у пам'яті процесу.

Go флот

  • Менше великих реплік (1 репліка ≈ всі ядра).
  • round robin / weight=2 для потужніших хостів.
  • Немає менеджера воркерів усередині — restart-політика Docker.
  • GOMAXPROCS узгоджений із квотою CPU (automaxprocs).

Гібридний флот за одним Nginx

  • /api/chat → upstream Node.js з least_conn;
  • /api/reports → upstream Go з round robin;
  • /static → кеш Nginx без застосунків;
  • /ws → ip_hash для стабільності WebSocket.

JWT (тема 8) — контракт гетерогенної групи: жоден запит не прив'язаний до копії чи мови. Додавання репліки — операція масштабування, а не подія архітектури.
