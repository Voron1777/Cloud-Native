Анатомія кібератак

Безпека — не адитивний шар після розробки, а системна інженерна дисципліна, що проєктується разом з архітектурою. Кожен HTTP-ендпоінт, SQL-запит та токен — частина поверхні атаки (Attack Surface).

Переважна більшість успішних зломів використовує не вразливості нульового дня, а банальні інженерні помилки:

  • ін'єкції (SQL, NoSQL, OS-команд, XSS);
  • слабка автентифікація та компрометація секретних ключів;
  • слабкі алгоритми хешування паролів;
  • помилкова конфігурація розгортання.

Принципи інженерної безпеки

  • Defense in Depth — багатошарова ешелонована оборона: компрометація одного шару не означає злам системи.
  • Least Privilege — кожен компонент володіє мінімально необхідними правами.
  • Fail-Safe Defaults — будь-яка помилка за замовчуванням блокує доступ.
  • Zero Trust — жодної імпліцитної довіри: кожен запит автентифікується, незалежно від джерела.

Модель загроз STRIDE: Spoofing · Tampering · Repudiation · Information Disclosure · Denial of Service · Elevation of Privilege — кожна категорія маплюється на контрзахід (автентифікація, підписи, аудити, шифрування, rate limiting, RBAC).

OWASP Top 10 — орієнтир пріоритизації

  • A01 Broken Access Control — порушення контролю доступу.
  • A02 Cryptographic Failures — слабкі хеші, секрети у відкритому вигляді.
  • A03 Injection — SQL / NoSQL / OS-команди / XSS.
  • A05 Security Misconfiguration — помилкова конфігурація.
  • A07 Identification & Authentication Failures — помилки ідентифікації.

Лекція охоплює контрзаходи для кожної категорії у стеках Node.js та Go.

Безстатусна безпека — вимога Cloud-native

Stateful (сесії)

  • Стан сесій — у пам'яті сервера.
  • Балансувальник зобов'язаний тримати sticky sessions.
  • Падіння інстансу → втрата сесій.
  • Не масштабується за віссю X.

Stateless (JWT)

  • Ідентифікаційний стан — у самому токені.
  • Будь-який інстанс обробляє будь-який запит.
  • Жодного централізованого сховища сесій.
  • Передумова горизонтального масштабування.

JWT — підписане твердження, не шифрований контейнер: читається будь-ким, підробляється тільки без ключа.

Структура JWT: header.payload.signature

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9   ← header  (alg, typ)
.eyJzdWIiOiIxMjM0Iiwicm9sZSI6ImFkbWluIiwiaWF0IjoxNzAwMH0   ← payload (claims)
.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c   ← signature (HMAC-SHA256)

Header: алгоритм підпису (alg) та тип (typ). Payload: claims — зареєстровані (iss, sub, exp, iat, jti) та приватні (role, permissions). Signature:

HMAC-SHA256(base64url(header) + "." + base64url(payload), secret)

Будь-яка модифікація payload → підпис стає невалідним.

Алгоритми та життєвий цикл токенів

HS256 (HMAC)

  • Один симетричний секрет.
  • Простий у конфігурації.
  • Оптимально для моноліту.
  • Секрет знає кожен перевіряючий.

RS256 (RSA)

  • Приватний ключ підписує, публічний верифікує.
  • Споживачі не можуть підписати токен.
  • Стандарт мікросервісної архітектури.
  • Сумісний з Authorization Server.

Практика: access-токен 15 хв + refresh-токен 7 днів, з окремими секретами → мінімальне вікно зловживання при компрометації.

JWT у Node.js — генерація токенів

const jwt = require('jsonwebtoken');

function generateTokens(user) {
  const payload = {
    sub: user.id,           // зареєстрований claim — ID суб'єкта
    role: user.role,        // приватний claim — для авторизації
  };

  // Короткоживучий access-токен (15 хвилин)
  const accessToken = jwt.sign(payload, process.env.JWT_SECRET, {
    algorithm: 'HS256',
    expiresIn: '15m',
    issuer: 'app',
  });

  // Довгоживучий refresh-токен (7 днів) з окремим секретом
  const refreshToken = jwt.sign(
    { sub: user.id },
    process.env.JWT_REFRESH_SECRET,
    { algorithm: 'HS256', expiresIn: '7d' }
  );

  return { accessToken, refreshToken };
}

Node.js — ланцюжок фільтрів безпеки (Express)

// Фільтр 1: обов'язкова автентифікація
function requireAuth(req, res, next) {
  const header = req.headers.authorization || '';
  if (!header.startsWith('Bearer ')) {
    return res.status(401).json({ error: 'Unauthorized' });
  }
  try {
    // Явний перелік алгоритмів — захист від атаки alg=none
    req.user = jwt.verify(header.slice(7), process.env.JWT_SECRET,
      { algorithms: ['HS256'] });
    next();                     // передача наступному фільтру
  } catch {
    return res.status(401).json({ error: 'Invalid or expired token' });
  }
}

// Фільтр 2: авторизація за роллю (RBAC)
function requireRole(...roles) {
  return (req, res, next) => {
    if (!roles.includes(req.user.role)) {
      return res.status(403).json({ error: 'Forbidden' });
    }
    next();
  };
}

// Композиція фільтрів на маршруті
app.get('/api/admin/stats', requireAuth, requireRole('admin'), handler);

JWT у Go — типізовані claims

package auth

import (
  "os"
  "time"

  "github.com/golang-jwt/jwt/v5"
)

// Claims — статична перевірка на етапі компіляції
type Claims struct {
  Role string `json:"role"`
  jwt.RegisteredClaims
}

func GenerateAccessToken(userID, role string) (string, error) {
  claims := Claims{
    Role: role,
    RegisteredClaims: jwt.RegisteredClaims{
      Subject:   userID,
      ExpiresAt: jwt.NewNumericDate(time.Now().Add(15 * time.Minute)),
      IssuedAt:  jwt.NewNumericDate(time.Now()),
      Issuer:    "app",
    },
  }
  token := jwt.NewWithClaims(jwt.SigningMethodHS256, claims)
  return token.SignedString([]byte(os.Getenv("JWT_SECRET")))
}

Go — Gin middleware (фільтр безпеки)

func AuthMiddleware() gin.HandlerFunc {
  return func(c *gin.Context) {
    header := c.GetHeader("Authorization")
    if len(header) < 8 || header[:7] != "Bearer " {
      c.AbortWithStatusJSON(401, gin.H{"error": "unauthorized"})
      return
    }
    claims := &Claims{}
    _, err := jwt.ParseWithClaims(header[7:], claims,
      func(t *jwt.Token) (interface{}, error) {
        // Верифікація алгоритму — захист від атаки alg=none
        if _, ok := t.Method.(*jwt.SigningMethodHMAC); !ok {
          return nil, errors.New("unexpected signing method")
        }
        return []byte(os.Getenv("JWT_SECRET")), nil
      })
    if err != nil {
      c.AbortWithStatusJSON(401,
        gin.H{"error": "invalid or expired token"})
      return
    }
    c.Set("userID", claims.Subject)
    c.Set("role", claims.Role)
    c.Next()
  }
}

Захист секретних ключів

  • Ключі ніколи не хардкодяться і не комітяться в Git — .env у .gitignore.
  • Тільки процесні змінні: process.env (Node.js), os.Getenv() (Go).
  • HS256: секрет ≥ 256 біт випадкових даних.
  • Мікросервіси → RS256: споживачі мають лише публічний ключ.
  • Корпоративний рівень → HashiCorp Vault / AWS KMS з ротацією.

Хешування паролів — чому не MD5/SHA-256?

Пароль зберігається лише через одностороннє хешування (one-way hash): дайджест не відновлюється, при логіні звіряються хеші.

Швидкі хеші (MD5, SHA-1, SHA-256) непридатні для паролів:

  • мільярди обчислень/сек на GPU → тривіальний brute force;
  • однакові пароли → однакові хеші → rainbow tables (попередньо обчислені відповідники).

Вони проєктувались для швидкої перевірки цілісності даних — швидкість тут стає вразливістю, а не перевагою.

Контрзаходи: сіль та повільні KDF

  • Випадкова сіль (16-32 байти на кожен пароль) — анулює rainbow tables;
  • Повільні адаптивні KDF з cost factor — bcrypt (10-12), scrypt (N=16384, memory-hard), PBKDF2 (600k+ ітерацій);
  • timing-safe порівняння — захист від timing-атак.

Кожне хешування свідомо сповільнюється до десятків-сотень мілісекунд — перебір паролів стає економічно невигідним.

Node.js — scrypt з вбудованого crypto

const crypto = require('crypto');
const SCRYPT = { N: 16384, r: 8, p: 1, keylen: 64 };

function hashPassword(password) {
  return new Promise((resolve, reject) => {
    // Криптостійка випадкова сіль — 16 байтів на кожен пароль
    const salt = crypto.randomBytes(16);
    crypto.scrypt(password, salt, SCRYPT.keylen, SCRYPT,
      (err, hash) => {
        if (err) return reject(err);
        // Формат зберігання: схема:сіль:хеш
        resolve('scrypt:' + salt.toString('hex')
                       + ':' + hash.toString('hex'));
      });
  });
}

async function verifyPassword(password, stored) {
  const [scheme, saltHex, hashHex] = stored.split(':');
  const hash = await new Promise((resolve, reject) => {
    crypto.scrypt(password, Buffer.from(saltHex, 'hex'),
      SCRYPT.keylen, SCRYPT,
      (err, derived) => err ? reject(err) : resolve(derived));
  });
  // timingSafeEqual — порівняння постійного часу
  return crypto.timingSafeEqual(Buffer.from(hashHex, 'hex'), hash);
}

Node.js — bcrypt (промисловий стандарт)

const bcrypt = require('bcrypt');

async function register(password) {
  // Cost factor 12 → близько 2^12 (4096) раундів;
  // сіль генерується та вбудовується автоматично
  return bcrypt.hash(password, 12);   // '$2b$12$...'
}

async function login(password, storedHash) {
  return bcrypt.compare(password, storedHash);
}

Cost factor — головний налаштувальний параметр: щоразу +1 подвоює час обчислення. Значення 10 — розробка, 12 — промислові системи (десятки-сотні мс на хеш).

Go — пакет x/crypto/bcrypt

package auth

import "golang.org/x/crypto/bcrypt"

// Реєстрація: хешування з автоматичною сіллю
func HashPassword(password string) (string, error) {
  // Cost factor 12 → близько 4096 раундів bcrypt
  hash, err := bcrypt.GenerateFromPassword([]byte(password), 12)
  if err != nil {
    return "", err
  }
  // Формат: $2a$12$<сіль><хеш> — сіль вбудована в результат
  return string(hash), nil
}

// Логін: верифікація (порівняння постійного часу)
func CheckPassword(password, storedHash string) bool {
  err := bcrypt.CompareHashAndPassword(
    []byte(storedHash), []byte(password))
  return err == nil   // nil → пароль валідний
}

bcrypt.DefaultCost = 10; промислові системи — 12. Розширення стандартної бібліотеки Go.

Кореневий дефект: неперевірені дані користувача інтерпретуються як частина SQL-синтаксису.

Універсальний контрзахід — параметризовані запити (prepared statements): значення передається окремо від тексту запиту, сервер БД гарантує, що параметр ніколи не виконується як SQL.

Go — статична типізація як захист

  • Немає eval / new Function — рядок не можна перетворити на виконуваний код.
  • Десеріалізація JSON у структуру з фіксованими полями — невідомі ключі (в т.ч. __proto__) ігноруються.
  • Prototype pollution структурно неможливий.
  • Єдиний вектор — fmt.Sprintf у SQL: блокується дисципліною placeholder-ів та go vet.

У Node.js ці захисти реалізуються вручну (allowlist, санітизація merge), у Go — гарантуються мовою.

XSS — Cross-Site Scripting

Ін'єкція шкідливого JavaScript у сторінки інших користувачів:

  • Stored XSS — скрипт зберігається у БД (поле коментаря) і виконується у кожного відвідувача;
  • Reflected XSS — payload відбивається у відповіді на запит;
  • DOM-based XSS — виконується в браузері через небезпечні innerHTML / document.write.

Контрзаходи:

  • Екранування (escaping) всіх динамічних даних перед виводом в HTML;
  • Content Security Policy (CSP) — скрипти лише з довірених джерел, inline-код заборонений.

XSS — helmet та CSP у Node.js

const helmet = require('helmet');
app.use(helmet());

// Content Security Policy — дозвіли на ресурси сторінки
app.use(helmet.contentSecurityPolicy({
  directives: {
    defaultSrc: ["'self'"],
    scriptSrc: ["'self'"],        // скрипти — лише власні
    objectSrc: ["'none'"],
    frameAncestors: ["'none'"],   // заборона вбудовування в iframe
  },
}));

// Екранування динамічного вмісту (stored XSS)
function escapeHtml(str) {
  return str
    .replace(/&/g, '&amp;')
    .replace(/</g, '&lt;')
    .replace(/>/g, '&gt;')
    .replace(/"/g, '&quot;')
    .replace(/'/g, '&#x27;');
}

CSRF — Cross-Site Request Forgery

Механізм: браузер автоматично прикріплює cookies → шкідливий сайт надсилає запит від імені жертви (переказ коштів, зміна email паролю).

Контрзаходи:

  • CSRF-токени (double-submit cookie / synchronizer token) — випадкове значення звіряється сервером;
  • SameSite=Strict/Lax — cookies не прикріплюються до поперечних запитів;
  • перевірка заголовка Origin;
  • JWT у заголовку Authorization → вбудовано імунний до CSRF (браузер його не прикріплює).

CSRF — double-submit cookie + SameSite

app.get('/api/transfer/form', (req, res) => {
  const csrfToken = crypto.randomBytes(32).toString('hex');
  // Cookie читається JS-клієнтом та дублюється в заголовку
  res.cookie('XSRF-TOKEN', csrfToken, {
    sameSite: 'strict',   // заборона поперечних запитів
    secure: true,          // лише HTTPS
    httpOnly: false,
  });
  res.json({ csrfToken });
});

app.post('/api/transfer', (req, res) => {
  // Cookie та заголовок мусять співпасти
  if (req.get('X-CSRF-Token') !== req.cookies['XSRF-TOKEN']) {
    return res.status(403).json({ error: 'CSRF validation failed' });
  }
  // ... обробка операції
});

Clickjacking — перехоплення кліків

Атака (UI redressing): цільовий сайт вбудовується у прозорий iframe поверх підробленого інтерфейсу — жертва бачить кнопку «Отримати приз», а натискає кнопку цільового сервісу («Передати права адміністратора»).

Захист: заборона вбудовування сторінок у фрейми:

  • X-Frame-Options: DENY — браузер блокує вбудовування сторінки в iframe;
  • CSP: frame-ancestors 'none' — сучасна альтернатива з тоншим контролем джерел.

Заголовки безпеки — Gin middleware

// Gin — централізований фільтр заголовків безпеки
func SecurityHeaders() gin.HandlerFunc {
  return func(c *gin.Context) {
    c.Header("X-Frame-Options", "DENY")          // clickjacking
    c.Header("X-Content-Type-Options", "nosniff")
    c.Header("Content-Security-Policy",
      "default-src 'self'; frame-ancestors 'none'")
    c.Header("Strict-Transport-Security",
      "max-age=31536000; includeSubDomains")     // примусовий HTTPS
    c.Header("Referrer-Policy", "no-referrer")
    c.Next()
  }
}

Захист інтелектуальної власності коду

Проблема: розгорнутий артефакт доступний третім сторонам.

Node.js

  • Вся бізнес-логіка — читабельний текст JavaScript.
  • Захист: обфускація (javascript-obfuscator, аналог Obfuscar для .NET).

Go

  • Нативний бінарник, але за замовчуванням містить таблицю символів та DWARF.
  • Захист: стріпінг -ldflags="-s -w" + -trimpath.

Обфускація Node.js — javascript-obfuscator

npm install --save-dev javascript-obfuscator

npx javascript-obfuscator src/server.js \
  --output dist/server.js \
  --compact true \
  --control-flow-flattening true \
  --dead-code-injection true \
  --string-array true \
  --string-array-encoding base64 \
  --self-defending true

wc -c src/server.js dist/server.js    # розмір до/після

Перетворення: control flow flattening (лінійна логіка → лабіринт) · dead code injection · string array з base64 · self-defending (ламається при beautify).

Важливо: обфускація — не шифрування: вона не робить аналіз неможливим, а економічно невигідним.

Обфускація — до / після

// ДО — читабельна бізнес-логіка:

}

Go — стріпінг бінарників

# Стандартна збірка — з символами та DWARF-інформацією
go build -o bin/app-full ./cmd/server

# Стріпінг: -s (таблиця символів), -w (DWARF-дебаг)
go build -ldflags="-s -w" -trimpath -o bin/app ./cmd/server

# Порівняння розмірів: типово 25-30% економії
ls -lh bin/
#   app-full   18M   (імена функцій + дебаг + шляхи збірки)
#   app        12M   (стрипнутий бінарник)

# Верифікація: file підтверджує "stripped"
file bin/app
#   bin/app: ELF 64-bit ... statically linked, stripped

# Опційно: UPX-стиснення фінального артефакту
upx --best bin/app

-s -w — позбавляють імен функцій; -trimpath — видаляє шляхи збірки (робочі директорії, логіни розробників).

Реліз-конвеєр захисту артефактів

Multi-stage Dockerfile — обфускація Node.js та стріпінг Go виконуються на етапі збірки CI/CD, не чіпаючи вихідний код розробників:

  • Етап 1 (builder): збирає захищений артефакт — обфускований dist/ або стрипнутий бінарник;
  • Етап 2 (production): містить лише захищений артефакт, без вихідного коду та дебаг-інформації;
  • Вихідний код з осмисленими іменами залишається у приватному просторі розробки та Git.

У промислове середовище потрапляє лише захищений артефакт — вимога реліз-інжинірингу курсу.

Вибір технології під задачу

Node.js

  • Найбагатша екосистема middleware безпеки.
  • helmet — заголовки одним рядком.
  • Швидке прототипування безпечного API.
  • Обмеження: prototype pollution та eval — специфічні вектори, дисципліна валідації на кожному обробнику.

Go

  • Цілі класи атак усунуті компіляцією (без eval).
  • Статична типізація claims та JSON-полів.
  • Стріпінг — найкращий захист ІВ у класі.
  • Оптимально для мікросервісів з жорсткими вимогами безпеки.

Спільна модель безпеки

Обидва стеки використовують ідентичний стандарт JWT:

  • API-шлюз на Go верифікує токени, видані сервісами Node.js, — спільний секрет HS256 або публічний ключ RS256;
  • Єдиний центр видачі токенів (Authorization Server) + гетерогенні ресурсні сервіси — індустріальний патерн;
  • Безпека стає контрактом між сервісами, а не властивістю окремої мови.
