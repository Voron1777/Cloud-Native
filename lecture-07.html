Рівень персистентності

Persistence Layer — один із найвідповідальніших архітектурних шарів серверної системи. Визначає, як дані зберігаються, структуруються та повертаються у відповідь на запити бізнес-логіки.

Вибір між реляційними (SQL) та нереляційними (NoSQL) БД — це інженерний компроміс, що залежить від:

  • типу навантаження (OLTP / read-heavy / write-heavy);
  • структури даних та вимог до схеми;
  • вимог до консистентності (ACID vs eventual consistency);
  • очікуваного масштабу системи.

SQL vs NoSQL — компроміси

Реляційні (MySQL, PostgreSQL)

  • Жорстка схема даних, зовнішні ключі.
  • Транзакційна цілісність ACID.
  • Потужна декларативна мова SQL.
  • Оптимальні для складних взаємозв'язків сутностей, фінансових транзакцій, ERP.
  • Обмеження: важке горизонтальне масштабування, чутливість до змін схеми.

Нереляційні (MongoDB)

  • Гнучка схема (schema-less).
  • Природне горизонтальне масштабування (sharding).
  • Висока пропускна здатність для write-heavy.
  • BSON-документи маплюються на об'єкти JS/Go без ORM.
  • Недоліки: слабка підтримка складних join, обмежені транзакції між колекціями.

CAP-теорема та моделі консистентності

CAP-теорема (Consistency, Availability, Partition tolerance): у разі мережевого розділення (network partition) система гарантує лише одну з двох властивостей — C або A.

  • Реляційні БД — орієнтовані на консистентність (CP).
  • NoSQL — часто обирають доступність (AP).

Настроюваний рівень консистентності:

  • PostgreSQL: рівні ізоляції транзакцій (Read Uncommitted → Serializable).
  • MongoDB: read concern (local, majority, linearizable), write concern (w:1, w:majority).

Банківські операції → сильна консистентність; лайки, коментарі, логи → eventual consistency.

Критерії вибору сховища

  • OLTP (короткі транзакції, складні зв'язки) → реляційні БД.
  • Read-heavy з гнучкою структурою → документо-орієнтовані сховища.
  • Write-heavy з неструктурованими даними → NoSQL.

Вибір базується на аналізі: типу навантаження, структури даних, вимог до консистентності та очікуваного масштабу.

Polyglot persistence

Використання кількох типів сховищ у межах одного застосунку:

  • Профілі та транзакції → PostgreSQL;
  • Логи подій, меседжі чату → MongoDB;
  • Сесійні дані → Redis.

Кожен тип даних використовує оптимальне сховище, але ускладнює інфраструктуру та вимагає чіткої архітектурної ізоляції рівня доступу.

Нативні драйвери

Робота на рівні нативних драйверів (raw drivers) — максимальний контроль над виконанням запитів та мінімальні накладні витрати.

На відміну від ORM, які абстрагують SQL за шаром об'єктів, нативні драйвери дозволяють писати прямі SQL-запити. ORM часто генерують неоптимальні запити та приховують реальну вартість звернень до БД.

Node.js

  • mysql2 — MySQL (Promise API).
  • pg — PostgreSQL (власний пул).
  • mongodb — офіційний драйвер.

Go

  • database/sql — універсальний інтерфейс.
  • go-sql-driver/mysql — MySQL.
  • lib/pq, jackc/pgx — PostgreSQL.
  • go.mongodb.org/mongo-driver.

Нативні драйвери Node.js

// PostgreSQL через pg
const { Pool } = require('pg');

// MongoDB через mongo-driver
func connectMongo() (*mongo.Client, error) {

    opts := options.Client().ApplyURI("mongodb://localhost:27017")
    client, err := mongo.Connect(ctx, opts)
    if err != nil { return nil, err }
    return client, nil
}

Connection Pools

Connection Pool — критичний механізм оптимізації у високонавантажених системах.

Встановлення нового TCP-з'єднання до БД: handshake, автентифікація, ініціалізація сесії — 10-50 мс. Pool утримує відкриті з'єднання та повторно використовує їх → затримка до мікросекунд.

  • Занадто малий пул → черга очікування з'єднань.
  • Занадто великий пул → вичерпання лімітів БД та RAM.

Практичне правило: кількість з'єднань ≈ кількість конкурентних запитів, що одночасно очікують відповіді від БД.

  • Node.js (один потік Event Loop): 10-20 з'єднань.
  • Go (тисячі goroutines): 25-50 з'єднань.

Connection Pool у Node.js (1/2)

const { Pool } = require('pg');
const pool = new Pool({
  host: 'localhost', port: 5432, database: 'appdb',
  user: 'appuser', password: 'secret',
  max: 20,                    // макс. 20 одночасних з'єднань
  idleTimeoutMillis: 30000,   // закрити неактивне через 30с
  connectionTimeoutMillis: 2000,
});

// pool.query() автоматично бере та повертає з'єднання
async function findById(id) {
  const res = await pool.query(
    'SELECT * FROM users WHERE id = $1', [id]);
  return res.rows[0];
}

Connection Pool у Node.js (2/2)

// Ручне отримання з'єднання для транзакцій
const client = await pool.connect();
try {
  await client.query('BEGIN');
  await client.query(
    'UPDATE accounts SET balance = balance - 100 WHERE id = $1', [1]);
  await client.query(
    'UPDATE accounts SET balance = balance + 100 WHERE id = $1', [2]);
  await client.query('COMMIT');
} catch (e) {
  await client.query('ROLLBACK');
  throw e;
} finally {
  client.release();   // обов'язково повернути в пул
}

pool.query() — для одиночних запитів (авто-checkout). pool.connect() — для транзакцій (ручне керування + release()).

Connection Pool у Go

package main

import (
    "database/sql"
    "time"
    _ "github.com/go-sql-driver/mysql"
)

func newPool() *sql.DB {
    db, err := sql.Open("mysql",
        "appuser:secret@tcp(localhost:3306)/appdb?parseTime=true")
    if err != nil { panic(err) }
    db.SetMaxOpenConns(25)                  // макс. відкритих
    db.SetMaxIdleConns(5)                   // неактивних у пулі
    db.SetConnMaxLifetime(5 * time.Minute)  // час життя
    db.SetConnMaxIdleTime(2 * time.Minute)  // час неактивності
    return db
}

// QueryRow — автоматично бере та повертає з'єднання
func getUser(db *sql.DB, id int) (string, error) {
    var name string
    err := db.QueryRow(
      "SELECT name FROM users WHERE id = ?", id,
    ).Scan(&name)
    return name, err
}

Go-пул автоматично розподіляє з'єднання між тисячами goroutines через внутрішні м'ютекси та черги.

CRUD у реляційних БД — Node.js (pg)

const { Pool } = require('pg');
const pool = new Pool({ connectionString: process.env.DATABASE_URL });

// CREATE
async function createUser(name, email) {
  const res = await pool.query(
    'INSERT INTO users (name, email) VALUES ($1, $2) RETURNING id',
    [name, email]);
  return res.rows[0].id;
}

// READ
async function getUser(id) {
  const res = await pool.query(
    'SELECT id, name, email, created_at FROM users WHERE id = $1',
    [id]);
  return res.rows[0] || null;
}

// UPDATE
async function updateUser(id, name) {
  await pool.query('UPDATE users SET name = $1 WHERE id = $2', [name, id]);
}

// DELETE
async function deleteUser(id) {
  await pool.query('DELETE FROM users WHERE id = $1', [id]);
}

Параметризовані запити ($1, $2) автоматично екранують значення → захист від SQL-ін'єкцій.

CRUD у реляційних БД — Go (1/2)

type User struct {
    ID        int
    Name      string
    Email     string
    CreatedAt time.Time
}

// CREATE
func CreateUser(db *sql.DB, name, email string) (int, error) {
    res, err := db.Exec(
        "INSERT INTO users (name, email) VALUES (?, ?)", name, email)
    if err != nil { return 0, err }
    id, _ := res.LastInsertId()
    return int(id), nil
}

// READ
func GetUser(db *sql.DB, id int) (*User, error) {
    u := &User{}
    err := db.QueryRow(
        "SELECT id, name, email, created_at FROM users WHERE id = ?", id,
    ).Scan(&u.ID, &u.Name, &u.Email, &u.CreatedAt)
    if err != nil { return nil, err }
    return u, nil
}

QueryRow — для запитів, що повертають один рядок (SELECT). Exec — для INSERT/UPDATE/DELETE. Scan() зчитує колонки у змінні.

CRUD у реляційних БД — Go (2/2)

// READ ALL — багато рядків через rows.Next()
func GetAllUsers(db *sql.DB) ([]User, error) {
    rows, err := db.Query("SELECT id, name, email FROM users")
    if err != nil { return nil, err }
    defer rows.Close()        // обов'язкове закриття rows

    var users []User
    for rows.Next() {
        var u User
        if err := rows.Scan(&u.ID, &u.Name, &u.Email); err != nil {
            return nil, err
        }
        users = append(users, u)
    }
    return users, nil
}

// UPDATE
func UpdateUser(db *sql.DB, id int, name string) error {
    _, err := db.Exec("UPDATE users SET name = ? WHERE id = ?", name, id)
    return err
}

// DELETE
func DeleteUser(db *sql.DB, id int) error {
    _, err := db.Exec("DELETE FROM users WHERE id = ?", id)
    return err
}

CRUD у MongoDB — Node.js (1/2)

const { MongoClient, ObjectId } = require('mongodb');
const client = new MongoClient('mongodb://localhost:27017');
const db = client.db('appdb');
const users = db.collection('users');

// CREATE — вставка одного документа
async function createUser(user) {
  const res = await users.insertOne({
    name: user.name, email: user.email,
    roles: ['user'], createdAt: new Date(),
  });
  return res.insertedId;
}

// READ — пошук за фільтром
async function findUsers(role) {
  return users.find({ roles: { $in: [role] } }).toArray();
}

// READ — пошук одного документа
async function findById(id) {
  return users.findOne({ _id: new ObjectId(id) });
}

CRUD у MongoDB — Node.js (2/2)

// UPDATE — модифікація полів через $set
async function updateUser(id, patch) {
  await users.updateOne(
    { _id: new ObjectId(id) },
    { $set: patch }
  );
}

// DELETE
async function deleteUser(id) {
  await users.deleteOne({ _id: new ObjectId(id) });
}

Оператори MongoDB: $eq, $gt, $lt — фільтрація; $set, $inc, $push — модифікація полів. Передаються як JS-об'єкти → природна інтеграція з мовою.

CRUD у MongoDB — Go (1/2)

type User struct {
    ID        primitive.ObjectID `bson:"_id"`
    Name      string             `bson:"name"`
    Email     string             `bson:"email"`
    Roles     []string           `bson:"roles"`
    CreatedAt primitive.DateTime `bson:"createdAt"`
}

type MongoUserRepo struct {
    col *mongo.Collection
}

func NewMongoUserRepo(db *mongo.Database) *MongoUserRepo {
    return &MongoUserRepo{col: db.Collection("users")}
}

// CREATE
func (r *MongoUserRepo) Create(ctx context.Context, u *User) error {
    res, err := r.col.InsertOne(ctx, u)
    if err != nil { return err }
    u.ID = res.InsertedID.(primitive.ObjectID)
    return nil
}

CRUD у MongoDB — Go (2/2)

// READ — пошук за ID
func (r *MongoUserRepo) FindByID(ctx context.Context, id string) (*User, error) {
    oid, _ := primitive.ObjectIDFromHex(id)
    u := &User{}
    err := r.col.FindOne(ctx, bson.M{"_id": oid}).Decode(u)
    return u, err
}

// READ — пошук за фільтром
func (r *MongoUserRepo) FindByRole(ctx context.Context, role string) ([]User, error) {
    cursor, err := r.col.Find(ctx, bson.M{"roles": bson.M{"$in": []string{role}}})
    if err != nil { return nil, err }
    defer cursor.Close(ctx)
    var users []User
    if err := cursor.All(ctx, &users); err != nil {
        return nil, err
    }
    return users, nil
}

bson-теги структур маплять поля документа MongoDB на поля Go. Запити — через bson.M (map) або bson.D (ordered). Усі методи приймають context.Context для контролю таймаутів.

CRUD у MongoDB — Go (3/3)

// UPDATE
func (r *MongoUserRepo) Update(ctx context.Context, id string, patch bson.M) error {
    oid, _ := primitive.ObjectIDFromHex(id)
    _, err := r.col.UpdateOne(ctx, bson.M{"_id": oid}, bson.M{"$set": patch})

}

// DELETE

Маскування логіки сховищ у Go — інтерфейси

Інтерфейси Go реалізують принцип інверсії залежностей (Dependency Inversion Principle).

  • Інтерфейс неявний — тип задовольняє інтерфейс, якщо реалізує всі його методи (structural typing / duck typing).
  • Інтерфейс визначається на боці споживача (consumer), а не постачальника (provider).

Для рівня персистентності інтерфейси дозволяють повністю маскувати конкретну технологію БД від бізнес-логіки. Сервіс залежить від абстрактного UserRepository, а не від *sql.DB або *mongo.Collection.

Переваги: (1) заміна БД без зміни бізнес-коду; (2) просте мокування у тестах; (3) підтримка поліглот-персистентності.

Repository pattern — інтерфейс та сервіс

// ===== ІНТЕРФЕЙС (контракт рівня сховища) =====
// Визначається на боці бізнес-логіки, не залежить від БД
type UserRepository interface {
    Create(ctx context.Context, name, email string) (string, error)
    FindByID(ctx context.Context, id string) (*User, error)
    FindAll(ctx context.Context) ([]User, error)
    Update(ctx context.Context, id, name string) error
    Delete(ctx context.Context, id string) error
}

// ===== СЕРВІС (бізнес-логіка) =====
// Залежить лише від інтерфейсу, не знає про конкретну БД
type UserService struct {
    repo UserRepository
}

func NewUserService(repo UserRepository) *UserService {
    return &UserService{repo: repo}
}

func (s *UserService) Register(name, email string) (string, error) {
    return s.repo.Create(context.Background(), name, email)
}

func (s *UserService) GetProfile(id string) (*User, error) {
    return s.repo.FindByID(context.Background(), id)
}

      "SELECT id::text, name, email FROM users WHERE id = $1", id,
    ).Scan(&u.ID, &u.Name, &u.Email)
    return u, err
}

Вибір технології під задачу

Node.js

  • I/O-інтенсивні API, швидке прототипування.
  • Єдиний стек JS/TS (клієнт + сервер).
  • Природний маппінг BSON на JS-об'єкти.
  • Async/await — лінійний читабельний код.
  • Обмеження: динамічна типізація → ризик runtime-помилок.

Go

  • Високонавантажені мікросервіси, сувора типізація.
  • Статична типізація (sql/bson-теги).
  • Інтерфейси — нативний Dependency Inversion.
  • Мокування без зовнішніх фреймворків.
  • Компіляція у нативний код, мінімальний оверхед.

Гібридний підхід

У практиці Cloud-native систем часто використовується гібридний підхід, що максимізує переваги кожної технології під відповідний тип навантаження:

  • Node.js — API-запити з MongoDB (JSON-документи маплюються безпосередньо на JS-об'єкти).
  • Go — транзакційні операції з PostgreSQL (статична типізація та інтерфейси для надійності фінансових операцій).

Таке розділення дозволяє кожному сервісу використовувати оптимальний стек під свій тип навантаження.
