Чому спостереження, а не відлагодження

Масштабування за віссю X (тема 9) зробило систему групою реплік за Nginx: жоден окремий лог не містить повної картини, а контейнери народжуються та зникають — приєднати відлагоджувач неможливо.

Моніторинг

  • Наперед сформульовані питання: «чи живий сервіс?»
  • Health checks, пороги алертів (тема 9).

Обсерваційність

  • Нові, наперед невідомі питання.
  • «Чому p95 зріс утричі після релізу?»

Обсерваційність — властивість системи, що дозволяє за логами, метриками та трейсами відновити внутрішній стан без нового розгортання.

Три стовпи обсерваційності

Логи (Logs)

  • Дискретні події: «що сталося в момент T».
  • Помилка автентифікації, запит до БД, старт процесу.

Метрики (Metrics)

  • Числові часові ряди: агрегований стан.
  • RPS, латентність, пам'ять — динаміка на осі часу.

Трейси (Traces)

  • Шлях одного запиту крізь усі сервіси.
  • Nginx → Express → Gin → PostgreSQL, з часом кожного сегмента.

Робочий цикл відлагодження

  • Алерт метрики → «частка 5xx зросла до 3%».
  • Трейс → «затримка у виклику go-api /api/reports».
  • Лог → «connection pool exhausted».

RED, USE та чотири золоті сигнали

RED — сервіси: Rate, Errors, Duration

  • Частота запитів, частка помилок, розподіл часу обробки.

USE — ресурси: Utilization, Saturation, Errors

  • Утилізація, насичення (черги), збої.

Золоті сигнали Google SRE

  • Latency — час відгуку (успішні окремо).
  • Traffic — інтенсивність навантаження.
  • Errors — порушення контракту сервісу.
  • Saturation — наскільки система «повна».

Насичення стеків курсу: Node.js — event loop lag (тема 1); Go — runnable-горутини, черги M:P:N (тема 2).

Метрики безпеки (тема 8): частка 401/403, невдалі логіни, спрацювання rate limit — аномалія цих рядів є раннім маркером атаки.

Централізоване логування — pino (Node.js)

Логи пишуть у stdout: Docker-драйвер json-file → Filebeat/Fluent Bit → Elasticsearch → Kibana (стек EFK). Кожен запис — один JSON-об'єкт, а не вільний текст.

const pino = require('pino');
const logger = pino({
  level: process.env.LOG_LEVEL || 'info',
  // redact: приховує секретні поля ще до запису (тема 8)
  redact: ['req.headers.authorization', '*.password'],
});

logger.info({ service: 'node-api', port: 3000 }, 'server started');

// Контекст запиту: middleware додає reqId до кожного запису
app.use((req, res, next) => {
  req.log = logger.child({ reqId: crypto.randomUUID() });
  req.log.info({ method: req.method, url: req.url }, 'request in');
  next();
});

Централізоване логування — slog (Go)

package main

import (
  "log/slog"
  "os"
)

// Структурований логер: JSON у stdout, як pino
var logger = slog.New(slog.NewJSONHandler(os.Stdout, &slog.HandlerOptions{
  Level: slog.LevelInfo,
}))

func main() {
  logger.Info("server started", "service", "go-api", "port", 8080)

  // Атрибути — типізовані пари ключ-значення
  logger.Error("db query failed",
    "op", "FindUserByEmail", "err", "connection refused")
}

Один формат обох стеків: логи Node.js та Go зливаються в єдиний централізований потік. Ключ до кореляції: middleware дописує у кожен запис trace_id (питання 3) — пошук за ним дає ланцюг подій одного запиту через всі сервіси.

Prometheus — архітектура збору

  • Pull-модель: сервер опитує (scrape) /metrics кожного застосунку кожні 15 с.
  • Багатовимірна модель даних: ряд = ім'я метрики + мітки: http_requests_total{method="GET",status="200"}.
  • Exporters: node_exporter (хост), postgres_exporter, nginx-exporter — сторонні системи у тому ж форматі.
  • Grafana — фронтенд дашбордів, запитує Prometheus мовою PromQL.

Стійкість pull-моделі: пропущені цикли не втрачають дані (лічильники продовжують зростати); нові репліки підхоплюються service discovery; нуль клієнтських буферів у застосунку.

Типи метрик Prometheus

# Exposition-формат: відповідь GET /metrics
# HELP http_requests_total Total HTTP requests
# TYPE http_requests_total counter
http_requests_total{method="GET",status="200"} 1027
http_requests_total{method="GET",status="500"} 3

# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_bucket{le="0.005"} 240
http_request_duration_seconds_bucket{le="0.01"}  533
http_request_duration_seconds_bucket{le="+Inf"}  1000
http_request_duration_seconds_count 1000
  • Counter — монотонний лічильник: частота подій через rate().
  • Gauge — миттєве значення: з'єднання, пам'ять.
  • Histogram — розподіл за бакетами: база перцентилів p50/p95/p99.

Інструментування Node.js — prom-client

const client = require('prom-client');
const register = new client.Registry();
// Метрики рантайму: heap V8, event loop lag
client.collectDefaultMetrics({ register, prefix: 'node_' });

const httpDuration = new client.Histogram({
  name: 'http_request_duration_seconds',
  help: 'Request latency in seconds',
  labelNames: ['method', 'route', 'status'],
  buckets: [0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5],
  registers: [register],
});

app.use((req, res, next) => {
  const end = httpDuration.startTimer({ method: req.method });
  res.on('finish', () =>
    end({ route: req.route?.path ?? 'unknown', status: res.statusCode }));
  next();
});

app.get('/metrics', async (_q, res) => {   // endpoint збору
  res.set('Content-Type', register.contentType);
  res.end(await register.metrics());
});

Інструментування Go — client_golang

var httpDuration = prometheus.NewHistogramVec(
  prometheus.HistogramOpts{
    Name:    "http_request_duration_seconds",
    Buckets: []float64{0.005, 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5},
  },
  []string{"method", "route", "status"},
)

func init() { prometheus.MustRegister(httpDuration) }

// Middleware для Gin: замір тривалості кожного запиту
func GinMetrics() gin.HandlerFunc {
  return func(c *gin.Context) {
    start := time.Now()
    c.Next()
    httpDuration.WithLabelValues(
      c.Request.Method, c.FullPath(),
      strconv.Itoa(c.Writer.Status()),
    ).Observe(time.Since(start).Seconds())
  }
}

// Обробник /metrics: канонічний promhttp
func MetricsHandler() http.Handler { return promhttp.Handler() }

Розподілене трасування — модель

Метрики показують ЩО деградувало; трейси — ДЕ саме. Один запит = один trace = дерево span-ів.

  • Span — атомарна операція: ім'я, старт, тривалість, статус, атрибути.
  • trace_id (128 біт) — ідентифікатор ланцюжка; parent_span_id — вкладеність сегментів.
  • Propagation: контекст подорожує HTTP-заголовком W3C Trace Context: перший сервіс генерує trace_id, наступні — успадковують.
GET /api/orders HTTP/1.1
traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01
# Формат: {version}-{trace-id (128 біт)}-{parent-span-id}-{flags}

OpenTelemetry (OTel) — vendor-neutral стандарт CNCF для логів, метрик і трейсів; Jaeger — платформа візуалізації трейсів.

OpenTelemetry — Node.js

SDK стартує до Express: автоінструментування прошиває http, Express, драйвери pg/mongodb/redis без змін у бізнес-коді.

// Node.js — tracing.js: ініціалізація ДО запуску Express
const { NodeSDK } = require('@opentelemetry/sdk-node');
const { OTLPTraceExporter } =
  require('@opentelemetry/exporter-trace-otlp-http');

const sdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter({
    url: 'http://jaeger:4318/v1/traces',
  }),
  // auto-instrumentations: http, express, pg, mongodb, redis
});
sdk.start();

OpenTelemetry — Go

TracerProvider з OTLP-експортером; otelhttp тягне контекст із вхідного запиту, ручні span-и додають бізнес-рівень.

// Go — OTLP-експортер + ручний span бізнес-рівня
exporter, _ := otlptracehttp.New(ctx,
  otlptracehttp.WithEndpoint("jaeger:4318"))
otel.SetTracerProvider(
  sdktrace.NewTracerProvider(sdktrace.WithBatcher(exporter)))

func ProcessOrder(ctx context.Context, order Order) {
  tr := otel.Tracer("orders")
  ctx, span := tr.Start(ctx, "orders.process")
  defer span.End()
  span.SetAttributes(attribute.String("order.id", order.ID))
}

Jaeger UI — waterfall: видно, що 700 мс із 750 мс запиту — очікування на lock у PostgreSQL, а не повільність Go.

Методологія коректного бенчмарку

  • Ізоляція середовища: генератор навантаження не конкурує із сервером за ядро CPU (окремий хост / квота контейнера).
  • Прогрів (warm-up): JIT V8, пули з'єднань (тема 7), кеші БД стабілізуються після тисяч перших запитів.
  • Фіксовані параметри: однакові версії, NODE_ENV=production, GOMAXPROCS за квотою (тема 9), keep-alive.
  • Координована омана (coordinated omission): ab чекає на відповідь перед наступним запитом — система сповільнюється, генератор «пропускає» трафік. k6 executor constant-arrival-rate тримає частоту подачі — хвости стають видимими.
  • Замір + спостереження: під час прогону дашборд Prometheus показує, що насичується першим (event loop, CPU-квота, пул БД).

Apache Benchmark (ab)

# 50000 запитів, 200 паралельних з'єднань, keep-alive
ab -k -n 50000 -c 200 \
   -H "Content-Type: application/json" \
   http://localhost:3000/api/orders

#   -n   загальна кількість запитів
#   -c   паралельні з'єднання (конкурентність)
#   -k   keep-alive: без перевстановлення TCP
#   -p/-T   тіло POST та Content-Type

Мінімалістичний ветеран з пакета apache2-utils: потік запитів на один URL + зведення (RPS, середній час, перцентилі). Ідеальний для точкових замірів маршрутів стенду.

50% = 38 мс, 99% = 94 мс — це хвіст латентності: кожен сотий користувач чекає в 2,5 раза довше за медіанного.

Правильна вимога: «p95 < 300 мс», а не «середній час < 300 мс» — середнє приховує хвіст, який і формує досвід користувачів.

k6 (Grafana Labs) — сценарії та thresholds

// bench.js — драбина навантаження з порогами якості
import http from 'k6/http';
import { check, sleep } from 'k6';

export const options = {
  stages: [   // розігрів 50 → робочі 200 → пік 500 → спад
    { duration: '30s', target: 50 },
    { duration: '2m',  target: 200 },
    { duration: '30s', target: 500 },
    { duration: '1m',  target: 0 },
  ],
  thresholds: {
    http_req_duration: ['p(95)<300'],  // fail: p95 > 300 мс
    http_req_failed:   ['rate<0.01'],  // fail: помилки > 1%
  },
};

export default function () {
  const res = http.get('http://localhost/api/orders');
  check(res, { 'status 200': (r) => r.status === 200 });
  sleep(0.2);
}

Thresholds = SLA кодом: реліз із деградованою латентністю не проходить CI. Запуск: k6 run bench.js; результати → JSON / Prometheus Remote Write → графіки деградації поруч із метриками системи.

RPS та перцентилі — чому середнє бреше

Осі експерименту

  • RPS — скільки запитів/с виконує система.
  • p50 — досвід типової запиту.
  • p95 / p99 — границя для 19 із 20 / кожного сотого.

Ключовий факт

  • Розподіл асиметричний: середнє розтягується викидами.
  • Перцентилі деградують раніше за RPS: запити в чергах — RPS ще на плато, p99 уже зріс.
  • Точка зламу p99 = фактичний ліміт продуктивності; SLA: «99% < 200 мс».

Насичення: Node.js — event loop lag перевищив поріг; Go — стрімкий ріст runnable-горутин (черги M:P:N).

Інтерпретація результатів

Node.js

  • p50 нижчий на легких I/O-маршрутах: нуль перемикань контексту.
  • Одна синхронна операція 300 мс зупиняє весь воркер → захист: пул libuv + моніторинг event loop lag.

Go

  • Хвіст стабільніший: горутини розподілені по всіх ядрах — деградація плато, а не обривом.
  • Ризик: розгін горутин на піках.

Висновок курсу: стеки доповнюють, а не конкурують. /api/chat (real-time) — Node.js; /api/reports (CPU) — Go; обидва за Nginx (тема 9) під спільним периметром безпеки (тема 8). Вибір — прогноз профілю навантаження, а не мода.

Реліз-інжиніринг: монолітний образ — пастка

Одностадійний Dockerfile тягне в промисловий рантайм все: компілятор, npm, кеші модулів, сирці, дебаг-символи.

  • Вага: golang:1.22 — понад 800 МБ; повільний деплой, дорогі реєстри.
  • Поверхня атаки: bash-утиліти всередині контейнера (тема 8).
  • Витоки: секрети та .env у шарах образу.
  • Недетермінованість: релізний артефакт залежить від середовища збірки.

Multi-stage build: builder з інструментарієм → рантайм отримує лише артефакт через COPY --from=builder. Промисловий рантайм не бачить ані компілятора, ані сирців.

Multi-stage Dockerfile — Go

# ---------- Етап 1: builder ----------
FROM golang:1.22-alpine AS builder
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
# Релізна збірка: стріпінг + відтворювані шляхи (тема 8)
RUN CGO_ENABLED=0 GOOS=linux go build \
    -ldflags="-s -w" -trimpath \
    -o /bin/server ./cmd/server

# ---------- Етап 2: runtime ----------
FROM gcr.io/distroless/static-debian12:nonroot
COPY --from=builder /bin/server /server
USER nonroot:nonroot
EXPOSE 8080
ENTRYPOINT ["/server"]

~15 МБ, без shell і пакетного менеджера: мінімальна поверхня атаки. CGO_ENABLED=0 — статичний бінарник; automaxprocs узгоджує GOMAXPROCS з квотою контейнера (тема 9).

Multi-stage Dockerfile — Node.js

# ---------- Етап 1: builder ----------
FROM node:20-alpine AS builder
WORKDIR /app
COPY package*.json ./
RUN npm ci                       # відтворюване з lock-файлу
COPY . .
# Релізне перетворення: обфускація сирцю (тема 8)
RUN npx javascript-obfuscator src --output dist \
    --compact true --self-defending true
RUN npm prune --omit=dev         # викинути dev-залежності

# ---------- Етап 2: runtime ----------
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY --from=builder /app/node_modules ./node_modules
COPY --from=builder /app/dist ./src
USER node
EXPOSE 3000
CMD ["node", "src/server.js"]

Секрети — лише через environment під час запуску (тема 8), ніколи в образ.

Фінальний реліз-стек курсового проєкту

services:
  node-api:
    build: ./node-api           # multi-stage (обфускація, тема 8)
    expose: ["3000"]            # лише внутрішня мережа (тема 9)
