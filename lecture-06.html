Неблокуючий I/O

Традиційний підхід (buffer-based): весь обсяг даних завантажується в RAM перед обробкою.

  • Обсяг даних може перевищувати доступну RAM → OOM (Out of Memory).
  • Зростання навантаження на Garbage Collector.
  • Деградація продуктивності всієї системи.

Неблокуючий I/O — система не очікує завершення операції, а обробляє результат асинхронно (callbacks, Promises, події). Один потік обслуговує тисячі конкурентних з'єднань.

Потокова обробка (Streaming)

Дані обробляються частинами (chunks) по мірі надходження, аналогічно конвеєру на виробництві.

  • Сталий рівень споживання RAM — O(1) за обсягом.
  • У пам'яті лише невелика порція (chunk), а не весь файл.
  • Зменшення Time to First Byte (TTFB) — перші дані надходять одразу.
  • Критично для Cloud-native: мережеві протоколи, файлові системи, БД, API.

Streams — повноцінна архітектурна парадигма з гарантованою верхньою межею споживання ресурсів.

Buffered vs Streaming

Буферний підхід — ❌

const fs = require('fs');
// Файл 2 ГБ → OOM
const data = fs.readFileSync('huge-file.json');
const parsed = JSON.parse(data);

Завантажує ВСЕ в пам'ять.

Потоковий підхід — ✅

const fs = require('fs');
const stream = fs.createReadStream('huge-file.json');
stream.on('data', (chunk) => {
  // В пам'яті лише ~64 КБ
  processChunk(chunk);
});

Обробляє частинами.

Моделі неблокуючого I/O

Подійна модель (Node.js)

  • Архітектура Reactor, єдиний Event Loop.
  • libuv повідомляє про завершення I/O.
  • Без перемикання контексту → десятки тисяч з'єднань.
  • Обмеження: блокуюча операція зупиняє весь Event Loop.

Багатопотокова (Go)

  • Легковагі goroutines (~2 КБ стек).
  • Планувальник M:N (goroutines на OS-потоки).
  • Goroutine блокується логічно — планувальник перемикається.
  • Ефективна для I/O та CPU-інтенсивних задач.

Node.js — конкурентність через асинхронність; Go — через паралелізм (CSP-модель каналів).

Streams у Node.js

Потоки (Streams) — базовий модуль Node.js, реалізує патерн лінивої обробки (lazy evaluation). Побудовані на EventEmitter.

Події життєвого циклу: 'data', 'end', 'error', 'close'.

Чотири типи потоків:

  • Readable — потік для читання (джерело даних).
  • Writable — потік для запису (приймач).
  • Duplex — двонаправлений (читання + запис, незалежні).
  • Transform — перетворювач (вихід = функція від входу).

Readable Stream

Джерело даних; абстрагує файл, мережеве з'єднання, HTTP-запит. Два режими:

Flowing — автоматична передача через подію 'data'.

const readable = fs.createReadStream('data.txt');
readable.on('data', (chunk) => {
  console.log('chunk:', chunk.length, 'байт');
});
readable.on('end', () => console.log('Завершено'));

Paused — контрольоване читання через read().

readable.on('readable', () => {
  let chunk;
  while (null !== (chunk = readable.read())) {
    processChunk(chunk);
  }
});

readableHighWaterMark — межа внутрішнього буфера (64 КБ за замовчуванням).

Writable Stream

Приймач даних. Основний метод — write(chunk), який повертає true/false:

  • true — буфер ще не перевищив writableHighWaterMark (16 КБ).
  • false — буфер заповнений, сигнал припинити генерацію даних → Backpressure.
const writable = fs.createWriteStream('output.txt');
function writeData() {
  let i = 0;
  function writeNext() {
    let canContinue = true;
    while (i < 100000 && canContinue) {
      canContinue = writable.write(`Рядок ${i++}\n`);
    }
    if (i < 100000) writable.once('drain', writeNext); // чекаємо звільнення
  }
  writeNext();
}
writable.on('finish', () => console.log('Запис завершено'));

Writable Stream — події

  • end([chunk][, callback]) — завершення запису; після виклику write() призводить до помилки.
  • 'finish' — усі дані успішно записані, внутрішній буфер звільнено.
  • 'drain' — буфер звільнився нижче writableHighWaterMark, потік готовий приймати нові дані.

Вбудовані Writable: fs.createWriteStream(), HTTP-відповідь res, process.stdout/stderr, zlib.createGzip().

Кастомний: успадкування від stream.Writable + реалізація _write(chunk, encoding, callback).

Duplex та Transform

Duplex — одночасно Readable + Writable. Читання та запис незалежні.

Приклади: TCP-сокет net.Socket, crypto.createCipheriv, zlib.createDeflate.

Transform — спеціалізація Duplex: вихід = перетворення входу.

Проміжна обробка (middleware) у конвеєрі: фільтрація, модифікація, агрегація.

const { Transform } = require('stream');
class FilterStream extends Transform {
  constructor(keyword) { super({ objectMode: true }); this.keyword = keyword; }
  _transform(chunk, encoding, callback) {
    const line = chunk.toString();
    if (line.includes(this.keyword)) this.push(line); // лише рядки з ключовим словом
    callback(); // обов'язковий виклик
  }
}
const filter = new FilterStream('ERROR');

.pipe() та pipeline()

.pipe() з'єднує вихід Readable з входом Writable і автоматично керує потоком (Backpressure).

❌ Небезпечно — .pipe() не обробляє помилки:

fs.createReadStream('input.gz')
  .pipe(zlib.createGunzip())
  .pipe(fs.createWriteStream('output.csv'));
// Витік пам'яті при помилці!

✅ Безпечно — stream.pipeline():

const { pipeline } = require('stream');
pipeline(
  fs.createReadStream('input.gz'),
  zlib.createGunzip(),
  fs.createWriteStream('output.csv'),
  (err) => {
    if (err) console.error(err);
  }
);

Конвеєри Streams = патерн Pipeline / Chain of Responsibility. ETL-процеси, стрімінг логів, обробка медіа, маршрутизація мікросервісів.

Backpressure — зворотний тиск

Backpressure виникає, коли швидкість виробника (producer) перевищує швидкість споживача (consumer).

  • Без механізму: швидкий виробник переповнює буфери → зростання RAM → OOM.
  • Сигнал виробнику призупинити генерацію, поки споживач не звільниться.
  • Аналогія: водопровід — якщо кран закритий, насос зменшує подачу.

Забезпечує сталий рівень споживання ресурсів усього конвеєра.

Backpressure у Node.js

readableHighWaterMark (64 КБ) та writableHighWaterMark (16 КБ) — межі буферів.

Ланцюг: write() повертає false → pause() → подія 'drain' → resume().

// Ручна реалізація Backpressure (без .pipe())
readable.on('data', (chunk) => {
  const canContinue = writable.write(chunk);
  if (!canContinue) {
    readable.pause();                 // буфер Writable заповнений
    writable.once('drain', () => {
      readable.resume();              // буфер звільнився
    });
  }
});
readable.on('end', () => writable.end());

Рекомендація: завжди використовувати stream.pipeline() для автоматичного управління Backpressure та помилками.

Backpressure у Go — канали

Канали (CSP-модель) — природний механізм Backpressure:

  • Небуферизований — блокує виробця до готовності споживача (нульовий тиск).
  • Буферизований (N) — до N елементів без блокування, далі — блокування.
func producer(out chan<- int) {
    for i := 0; i < 1000; i++ {
        out <- i              // блокується при повному буфері
    }
    close(out)
}
func processor(in <-chan int, out chan<- int) {
    for val := range in {
        out <- val * 2       // трансформація + блокування
    }
    close(out)
}
func main() {
    ch1 := make(chan int, 50) // буфер 50 → Backpressure автоматично
    ch2 := make(chan int, 50)
    go producer(ch1)
    go processor(ch1, ch2)
    for result := range ch2 { fmt.Println(result) }
}

Розмір буфера: ETL — 50-100, WebSocket broadcast — 10-20, логи — 1000-5000.

Системи реального часу (Real-time)

Real-time — затримка між подією на сервері та відображенням у клієнта мінімальна (мілісекунди).

На відміну від HTTP (запит-відповідь), потрібен push-механізм — сервер сам надсилає дані.

WebSockets — двонаправлені стійкі з'єднання поверх одного TCP-з'єднання.

  • Встановлюється один раз через HTTP Upgrade.
  • Лишається відкритим до явного закриття.
  • Усуває накладні витрати на HTTP-заголовки для кожного повідомлення.

WebSocket handshake (RFC 6455)

Клієнт → Сервер:

GET /chat HTTP/1.1
Host: server.example.com
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Key: dGhlIHNh...
Sec-WebSocket-Version: 13

Сервер → Клієнт:

HTTP/1.1 101 Switching Protocols
Upgrade: websocket
Connection: Upgrade
Sec-WebSocket-Accept: s3pPLMBi...

Фрейми: опкоди (0x1 текст, 0x2 бінарний, 0x8 close, 0x9 ping, 0xA pong), маскування XOR, payload до 2^64 байт.

Keep-alive: ping/pong виявляють розриви без очікування TCP-таймауту. Close handshake — узгоджене закриття з кодом (1000/1001/1006).

Менеджмент стійких з'єднань

  • Кожне з'єднання утримується відкритим весь сеанс → управління пам'яттю, виявлення неактивних, маршрутизація.
  • Hub/ConnectionManager: Map або Set з активними з'єднаннями та метаданими.
  • Heartbeat: інтервал 25-30 с, таймаут 60 с. Три пропущені → розірване з'єднання.
  • Reconnection клієнта з exponential backoff.

Горизонтальне масштабування

  • Stateful з'єднання прив'язані до інстансу.
  • Redis Pub/Sub або брокер (NATS, Kafka, RabbitMQ) для синхронізації між інстансами.
  • Nginx з ip_hash (sticky sessions).
  • Kubernetes: Ingress з WebSocket-підтримкою, HPA за кастомною метрикою, graceful shutdown.

WebSockets на Node.js: ws vs Socket.IO

ws

  • Мінімалістична, високопродуктивна.
  • Реалізує протокол WebSocket без абстракцій.
  • Повна сумісність з RFC 6455.
  • Для мікросервісів та стандартної сумісності.

Socket.IO

  • Високорівнева абстракція.
  • Кімнати (rooms), namespaces.
  • Автоперепідключення, fallback (long-polling).
  • Acknowledgments, broadcast.
  • Не сумісний з RFC 6455 — потрібен socket.io-client.

WebSocket-сервер на ws — init

const WebSocket = require('ws');
const http = require('http');
const express = require('express');

const app = express();
const server = http.createServer(app);
const wss = new WebSocket.Server({ server, path: '/ws' });
const clients = new Map();

wss.on('connection', (ws, req) => {
  const clientId = req.headers['x-client-id'] || Date.now();
  clients.set(clientId, ws);
  ws.on('message', (data) => {
    console.log('Повідомлення від', clientId, ':', data.toString());
  });
  ws.on('close', () => clients.delete(clientId));
  ws.on('error', (err) => console.error('Помилка:', err));
});
server.listen(3000);

wss.on('connection', (ws, req)) — ws — екземпляр WebSocket, req — HTTP-запит handshake (заголовки, IP).

WebSocket-сервер на ws — broadcast

function broadcast(message) {
  wss.clients.forEach((client) => {
    if (client.readyState === WebSocket.OPEN) {
      client.send(message);
    }
  });
}

// ConnectionManager (Map): реєстрація, видалення,
// відправка конкретному клієнту та broadcast-розсилка
// з метаданими (IP, кімнати, час підключення тощо).

Для управління множиною з'єднань — ConnectionManager або Map з активними з'єднаннями та метаданими.

Socket.IO — setup та кімнати

const { Server } = require('socket.io');
const http = require('http');
const server = http.createServer();
const io = new Server(server, {
  cors: { origin: '*' },
  pingInterval: 25000,
  pingTimeout: 60000,
});

const chat = io.of('/chat');              // namespace
chat.on('connection', (socket) => {
  socket.on('join-room', (roomId) => {
    socket.join(roomId);
    socket.to(roomId).emit('user-joined', socket.id);
  });
});

Rooms: socket.join(), socket.leave(), io.to('room').emit() — чат-кімнати, канали сповіщень, ігрові сесії.

Socket.IO — повідомлення та ack

  socket.on('message', (data) => {
    chat.to(data.roomId).emit('message', {
      user: socket.id,
      text: data.text,
      timestamp: Date.now()
    });
  });
  // Acknowledgment — підтвердження доставки
  socket.on('important-event', (payload, callback) => {
    processImportantEvent(payload);
    callback({ status: 'received' });
  });
  socket.on('disconnect', () => console.log('Відключився:', socket.id));
});

Namespaces (io.of('/chat'), io.of('/notifications')) — незалежні сервери на одному порті.

WebSockets на Go: gorilla/websocket

Де-факто стандарт WebSocket у Go. Повна підтримка RFC 6455: фрагментація, permessage-deflate, бінарні дані, закриття.

  • Кожне з'єднання — окрема goroutine для читання + окрема для запису (повнодуплексний режим).
  • ReadMessage() (блокуючий), WriteMessage().
  • Патерн виділеної goroutine-письменника (читає з каналу, записує в Socket).

Переваги Go: goroutines ~2 КБ → десятки тисяч з'єднань з мінімальним RAM; канали без м'ютексів; планувальник M:N розподіляє по ядрах CPU.

Hub-Client патерн на Go — Hub

Три компоненти: Hub (центральний вузол), Client (з'єднання), Handler (HTTP-обробник).

type Hub struct {
    clients     map[*Client]bool
    broadcast   chan []byte
    register    chan *Client
    unregister  chan *Client
}

Hub зберігає Map активних клієнтів та канали для реєстрації, відключення та розсилки повідомлень.

Hub-Client — Hub.Run()

func (h *Hub) Run() {
    for {
        select {
        case client := <-h.register:
            h.clients[client] = true
        case client := <-h.unregister:
            delete(h.clients, client)
            close(client.send)
        case message := <-h.broadcast:
            for client := range h.clients {
                select {
                case client.send <- message:
                default:                     // буфер переповнений
                    close(client.send)       // → закриваємо (Backpressure)
                    delete(h.clients, client)
                }
            }
        }
    }
}

default-гілка у broadcast — Backpressure на стороні сервера: повільний клієнт не затримує розсилку іншим.

Client: struct та serveWs

type Client struct {
    hub  *Hub
    conn *websocket.Conn
    send chan []byte // буферизований → Backpressure
}

func serveWs(hub *Hub, w http.ResponseWriter, r *http.Request) {
    conn, err := upgrader.Upgrade(w, r, nil)
    if err != nil { log.Println("Upgrade error:", err); return }
    client := &Client{hub: hub, conn: conn, send: make(chan []byte, 256)}
    hub.register <- client
    go client.writePump()
    go client.readPump()
}

send — буферизований канал (256 повідомлень) → вбудований Backpressure.

Client: readPump

func (c *Client) readPump() {
    defer func() { c.hub.unregister <- c; c.conn.Close() }()
    c.conn.SetReadDeadline(time.Now().Add(60 * time.Second))
    c.conn.SetPongHandler(func(string) error {
        c.conn.SetReadDeadline(time.Now().Add(60 * time.Second))
        return nil
    })
    for {
        _, message, err := c.conn.ReadMessage()
        if err != nil { break }
        c.hub.broadcast <- message
    }
}

Таймаути: read deadline 60 с, write deadline 10 с, ping 25-30 с. writePump — goroutine-письменник для запису з каналу send у Socket.

Продуктивність та масштабованість

  • Go в 3-5 разів вища пропускна здатність, в 5-10 разів менше споживання RAM за еквівалентного навантаження.
  • Компіляція Go в нативний код проти JIT-компіляції V8.
  • Node.js вимагає процесного масштабування (cluster) для утилізації всіх ядер CPU.
  • Stateful природа WebSocket → масштабування через sticky sessions + Redis Pub/Sub (або NATS/Kafka).

Вибір технології під задачу

Node.js + Socket.IO

  • Єдиний стек JS/TS (клієнт + сервер).
  • MVP та прототипи.
  • До 10 000 одночасних з'єднань.
  • Кімнати, namespaces, reconnection без зайвих зусиль.

Go + gorilla/websocket

  • Сотні тисяч одночасних з'єднань.
  • Мікросервісна архітектура.
  • Мінімальна затримка, максимальна пропускна здатність.
  • CPU-інтенсивна обробка повідомлень.
  • Обмежені ресурси (контейнери).
  • Сумісність з RFC 6455.

Гібридний підхід: Node.js — клієнтські з'єднання (Socket.IO), Go — високопродуктивне ядро; комунікація через Redis Pub/Sub або gRPC.
